# Безопасность: ПИН и шифрование

## Схема

```
ПИН ──PBKDF2-HMAC-SHA256(соль 16 байт, 600 000 итераций)──► 32 байта
                                                              │
                         ┌────────────────────────────────────┴────────────────────┐
                         ▼                                                         ▼
     эталон для проверки ПИНа (EncryptedSharedPreferences)          пароль SQLCipher для sandbox.db
```

Классы: `security/Pbkdf2.kt`, `security/PinManager.kt`, `security/SecurityModule.kt`, `data/db/DatabaseHolder.kt`.

## Хранение

EncryptedSharedPreferences, файл `secure_prefs`. Их создаёт `SecurityModule` с квалификатором `@SecurePrefs`, а `PinManager` получает их через `dagger.Lazy`, потому что инициализация обращается к Keystore и не должна выполняться на main-потоке. `MasterKey` использует схему `AES256_GCM` из Android Keystore. Имена ключей шифруются AES256-SIV, значения — AES256-GCM.

| Ключ | Содержимое |
|---|---|
| `pin_salt_v2` | соль, 16 байт, Base64 |
| `pin_pbkdf2` | производный ключ, 32 байта, Base64 |
| `pin_iterations` | число итераций (`Int`) |
| `pending_salt`, `pending_pbkdf2`, `pending_iterations` | временно, только во время миграции |
| `pin_salt`, `pin_sha256` | старая схема v1, удаляются после миграции |
| `failed_attempts` | число неудачных попыток входа подряд (`Int`), нет ключа = 0 |

Число итераций хранится вместе с хэшем. Если в будущем его повысить, уже установленные ПИНы продолжат проверяться со своим значением.

## PBKDF2

Код: `Pbkdf2.derive()`.

- Алгоритм PBKDF2-HMAC-SHA256 (RFC 8018), 600 000 итераций (рекомендация OWASP 2023), длина ключа 32 байта.
- **API 26+:** платформенный `SecretKeyFactory("PBKDF2WithHmacSHA256")` (нативная реализация в Conscrypt/BoringSSL).
- **API 24–25:** этого алгоритма в платформе нет, а minSdk проекта равен 24. Поэтому используется `Pbkdf2.fallback()` — прямая реализация RFC 8018 поверх `Mac("HmacSHA256")`. Она медленнее, но результат побитово совпадает.
- Совпадение проверяет `Pbkdf2Test`: тестовый вектор RFC 7914 §11 и сравнение с реализацией JDK на разных ПИНах, числах итераций и длинах ключа.

Вычисление занимает заметное время (от долей секунды до нескольких секунд на старых устройствах). Поэтому `AppViewModel` выполняет его на `Dispatchers.IO`, а на кнопке показывается индикатор (`AppUiState.busy`).

## Установка и проверка ПИНа

- `setPin()`: генерирует соль (`SecureRandom`), вычисляет PBKDF2 и записывает соль, хэш и число итераций одним `commit`. Повторный вызов бросает `IllegalStateException`.
- `verifyPin()`: пересчитывает PBKDF2 с сохранёнными солью и числом итераций и сравнивает через `MessageDigest.isEqual` (за постоянное время). Байты ПИНа обнуляются после использования.
- `databaseKey()`: возвращает сохранённый производный ключ без пересчёта. Поэтому ресивер открывает БД быстро и без ПИНа.
- `attemptUnlock()`: проверка ПИНа при входе с учётом лимита попыток (см. ниже). UI вызывает её, а не `verifyPin()`.

## Ограничение попыток

После **7 неверных ПИНов подряд** (`PinManager.MAX_ATTEMPTS`) все данные приложения уничтожаются. Верный ПИН обнуляет счётчик. При неверном вводе UI показывает только «Неверный ПИН-код», без предупреждения об очистке и без числа оставшихся попыток.

**Счётчик переживает смерть процесса и перезагрузку.** Он хранится в `secure_prefs` (`failed_attempts`), а `attemptUnlock()`:

1. если лимит уже исчерпан, сразу возвращает `LOCKED_OUT` и ПИН не проверяет;
2. увеличивает счётчик и синхронно пишет его (`commit`) **до** вычисления PBKDF2. Если запись не удалась, бросает исключение, и ПИН не проверяется. Поэтому убить процесс или перезагрузить телефон во время проверки, чтобы попытка «не засчиталась», не получится;
3. при верном ПИНе удаляет счётчик и возвращает `OK`, иначе `WRONG` или, на седьмой попытке, `LOCKED_OUT`.

**Очистка (`DataWiper.wipe()`).** Вызывается из `AppViewModel` при `LOCKED_OUT`, а также при старте, если `isLockedOut()` (прошлая очистка была прервана). Шаги идут в порядке, устойчивом к смерти процесса:

1. Room закрывается, `sandbox.db` удаляется (`deleteDatabase`, вместе с `-wal`/`-shm`/`-journal`).
2. Удаляется `secure_prefs` с ключом БД и счётчиком. Пока этот файл на месте, следующий запуск повторит очистку.
3. Удаляются все ключи приложения в Android Keystore, но **только если файла `secure_prefs` уже нет**: без мастер-ключа EncryptedSharedPreferences не открываются, и приложение не смогло бы стартовать.
4. `ActivityManager.clearApplicationUserData()` стирает остальные данные (как «Очистить данные» в настройках), **отзывает все runtime-разрешения** и завершает процесс.
5. Если системный вызов вернул `false`: вручную очищаются `databases`, `shared_prefs`, `files`, `no_backup`, `cache`, `code_cache` и каталоги во внешнем хранилище приложения. На API 33+ разрешения отзываются через `revokeSelfPermissionsOnKill`, затем процесс завершается. На API 24–32 в этом запасном пути разрешения отозвать нельзя.

После очистки приложение запускается как в первый раз: запрос разрешений, затем установка ПИНа.

## Миграция со схемы v1 (SHA-256)

Первая версия приложения хранила `SHA-256(соль ‖ ПИН)` и использовала его как ключ БД. Перешифровать такую БД без ПИНа невозможно, потому что новый ключ выводится из ПИНа. Поэтому миграция выполняется **при первом успешном входе** после обновления.

1. `verifyPin()` проверяет ПИН по старой схеме. До завершения миграции и UI, и ресивер работают со старым ключом.
2. `AppViewModel.unlock()` вызывает `DatabaseHolder.migrateKeyIfNeeded(pin)`. Под общей блокировкой:
   1. открытый экземпляр Room закрывается, потому что для rekey нужно единственное соединение;
   2. `PinManager.preparePending()` вычисляет PBKDF2 и сохраняет его как `pending_*` **до** изменения БД;
   3. `SqlCipherRekey.rekey()` открывает БД старым ключом, сливает WAL (`wal_checkpoint(TRUNCATE)`), переключает журнал в `DELETE` и вызывает `changePassword(newKey)`;
   4. `PinManager.commitPending()` одним `commit` делает `pending_*` основным ключом и удаляет `pin_sha256`, `pin_salt` и `pending_*`.
3. При следующем обращении Room откроет БД уже новым ключом и снова включит WAL.

**Если процесс умрёт посередине**, при следующем открытии БД (или следующей миграции) `recoverInterruptedMigration()` попробует открыть файл ключом `pending`. Если получится, значит rekey завершился, и выполняется `commitPending()`. Если нет, БД осталась на старом ключе, и выполняется `discardPending()`.

**Если rekey упадёт с ошибкой**, вход всё равно выполняется, ошибка пишется в лог, и БД продолжает работать со старым ключом. Попытка повторится при следующем входе.

**Защита от удаления файла.** Стандартный `DefaultDatabaseErrorHandler` SQLCipher удаляет файл БД при «повреждении», а неверный ключ выглядит именно так. Поэтому `SqlCipherRekey` открывает БД только с пустым обработчиком ошибок.

**Ограничение.** Если в момент миграции ресивер пишет событие, его соединение будет закрыто и запись этого события может не пройти (ошибка попадёт в лог).

## Модель угроз

Ресивер должен записывать события, пока UI заблокирован и ПИН не введён. Из-за этого ключ БД обязан быть доступен без участия пользователя. Получается следующее:

| От чего защищает | От чего не защищает |
|---|---|
| копирование файла `sandbox.db` с устройства или из бэкапа: без ключа файл не читается | злоумышленник, исполняющий код от имени приложения (root, отладка debug-сборки): он прочитает ключ из EncryptedSharedPreferences без ПИНа |
| просмотр данных в UI без знания ПИНа | извлечение ключа Keystore на устройствах без аппаратного хранилища |
| подбор ПИНа по утёкшему хэшу: PBKDF2 замедляет каждую попытку примерно в 600 000 раз по сравнению с одним SHA-256 | подбор короткого ПИНа на GPU: 10⁴ вариантов 4-значного ПИНа всё равно перебираются за минуты |

Иными словами, БД фактически защищена ключом Android Keystore, а ПИН закрывает только вход в UI. PBKDF2 усложняет перебор, если утекли и соль, и хэш, но не делает короткий цифровой ПИН стойким паролем.

## Ограничения и рекомендации

- **Лимит попыток действует только для UI.** Злоумышленник с root может сбросить счётчик или прочитать ключ БД напрямую (см. модель угроз). Задержки между попытками нет.
- **Ресивер не проверяет лимит.** Если очистка прервалась, события продолжат записываться до следующего запуска UI, который её завершит.
- **Сменить ПИН нельзя.** Механизм уже есть: `SqlCipherRekey` и `preparePending`/`commitPending`. Не хватает экрана и проверки старого ПИНа.
- **Deprecated API.** `androidx.security:security-crypto` 1.1.0 помечен deprecated. Возможная замена — собственное шифрование через Keystore (AES-GCM) поверх DataStore.
- **Бэкап отключён.** `allowBackup="false"`, кроме того `backup_rules.xml` и `data_extraction_rules.xml` исключают `database` и `sharedpref`. Ключ Keystore не переносится на другое устройство, поэтому восстановленные файлы всё равно были бы нечитаемы.
- **Сброс.** Если ПИН забыт, остаётся только «Очистить данные» приложения. БД и настройки при этом удаляются.
